# dprint-plugin-csharpier

[![npm version](https://img.shields.io/npm/v/@dprint/csharpier.svg)](https://www.npmjs.com/package/@dprint/csharpier) [![CI](https://github.com/dprint/dprint-plugin-csharpier/workflows/CI/badge.svg)](https://github.com/dprint/dprint-plugin-csharpier/actions?query=workflow%3ACI)

Wrapper around [CSharpier](https://github.com/belav/csharpier) in order to use it as a dprint plugin for C# and XML code formatting.

## Install

1. Install [dprint](https://dprint.dev/install/) 0.61.0 or later
1. Run `dprint init`
1. Run `dprint add csharpier`

It formats the same files as CSharpier: _.cs_ and _.csx_ files as C#, and _.csproj_, _.props_, _.targets_, _.slnx_, _.config_, _.xml_, _.xaml_, and _.axaml_ files as XML. Use dprint's [`"associations"`](https://dprint.dev/config/#associations) property to change this.

Like CSharpier, it doesn't format generated files (ex. _\*.g.cs_, _\*.designer.cs_, or a C# file starting with an `<auto-generated>` comment) unless `"includeGenerated"` is `true`.

## Configuration

Specify a "csharpier" configuration property in _dprint.json_ if desired:

```jsonc
{
  // etc...
  "csharpier": {
    "lineWidth": 120,
    "xml.indentWidth": 4
  }
}
```

| Property                   | CSharpier option           | Default                                                   |
| -------------------------- | -------------------------- | --------------------------------------------------------- |
| `lineWidth`                | `printWidth`               | `100`                                                     |
| `indentWidth`              | `indentSize`               | `4` for C# and `2` for XML                                |
| `useTabs`                  | `useTabs`                  | `false`                                                   |
| `newLineKind`              | `endOfLine`                | `"auto"`                                                  |
| `includeGenerated`         | `--include-generated`      | `false`                                                   |
| `xmlWhitespaceSensitivity` | `xmlWhitespaceSensitivity` | `"ignore"` for _.xaml_ and _.axaml_, otherwise `"strict"` |

The `lineWidth`, `indentWidth`, `useTabs`, and `newLineKind` properties use the global configuration when not specified, and may be specified for only C# or XML files by prefixing them with `csharp.` or `xml.` (ex. `"csharp.lineWidth": 120`).

The plugin doesn't read CSharpier's configuration files (_.csharpierrc_ or _.editorconfig_) because dprint plugins don't have access to the file system, so configure it in the dprint configuration file instead.

## Development

The plugin is compiled to a Wasm module using [NativeAOT-LLVM](https://github.com/dotnet/runtimelab/tree/feature/NativeAOT-LLVM).

1. Run the tests with `dotnet test`
1. Install version 29 of the [WASI SDK](https://github.com/WebAssembly/wasi-sdk/releases) and set the `WASI_SDK_PATH` environment variable to its directory.
1. Run `dotnet publish DprintPluginCSharpier -c Release -r wasi-wasm`, which creates _DprintPluginCSharpier/bin/Release/net10.0/wasi-wasm/publish/dprint-plugin-csharpier.wasm_
1. Reference the path to the _.wasm_ file in the `"plugins"` array of a dprint configuration file to try it out.
1. Update the generated configuration schema at _deployment/schema.json_ by running `dotnet test` with the `UPDATE=1` environment variable.
1. Run the tests that format with the _.wasm_ file in dprint by setting the `DPRINT_CSHARPIER_WASM_PATH` environment variable to its path and running `dotnet test --filter TestCategory=Wasm`. These use the `dprint` on the path or the executable at the `DPRINT_PATH` environment variable.

dprint only provides the WASI preview 1 functions to Wasm plugins, so the module must not import anything else. _DprintPluginCSharpier/ILLink.Substitutions.xml_ and the feature switches in the project file keep code that would import other functions out of the module.

### Releasing

Run the [release workflow](https://github.com/dprint/dprint-plugin-csharpier/actions/workflows/release.generated.yml), which bumps the version and pushes a tag. The CI workflow then publishes the GitHub release and the npm package for the tag.
